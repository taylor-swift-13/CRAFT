\subsection{Verification Objective}
\label{sec:overview:task}

A verification instance is a pair \((P,Q)\).
The program fragment \(P=(\phi_{\mathrm{pre}},B,S)\) contains the
precondition, loop guard, and loop body; \(Q\) is an assertion or
postcondition that must hold after the loop.  Let \(\mathcal R(P)\) denote the
states reachable at the loop head from inputs satisfying
\(\phi_{\mathrm{pre}}\).

The generator returns a conjunction \(I\) of ACSL loop-invariant clauses.
Frama-C/WP must prove initiation and preservation,
\[
  \phi_{\mathrm{pre}}\Rightarrow I
  \qquad\text{and}\qquad
  \{I\wedge B\}\,S\,\{I\}.
\]
It must also prove the original verification goal,
\[
  I\wedge\neg B\Rightarrow Q.
\]
The third condition matters because inductiveness alone admits predicates that
are correct but too weak to establish \(Q\).

\subsection{Information Available to the Generator}
\label{sec:overview:visibility}

\begin{definition}[Target-hidden loop verification]
The framework receives \((P,Q)\), but the generator and all intermediate
feedback receive only \(P\).  The generated invariant set is accepted only if
it satisfies all three obligations above after the original \(Q\) is restored.
\end{definition}

Before generation, complete ACSL \texttt{assert} and \texttt{ensures} clauses,
executable assertion calls, and conventional error-label names are removed.
Preconditions and executable loop semantics remain visible.  Candidate
generation, repair feedback, execution sampling, and Houdini filtering all use
this target-masked program.  The untouched full program is used only for final
verification.

The restriction concerns information flow, not output syntax: both
target-visible and target-hidden systems produce the same ACSL
\texttt{loop invariant} clauses.  Querying final proof success during training
would reveal information about \(Q\), so \sam{} instead derives its reward from
program executions (\S\ref{sec:method:sampler}).

\subsection{Scope and Motivating Example}

We focus on a single braced \texttt{while} loop over scalar C integers.
Arithmetic equalities and inequalities in this domain can be checked
automatically, allowing us to study invariant discovery without the additional
representation choices required by arrays, heaps, or recursive structures.
Nonlinear updates remain challenging because exact algorithmic guarantees are
largely concentrated on affine transition systems.

Consider the following abridged program:
\begin{lstlisting}
int x = 1, y = 1, c = 1;
while (c < k) {
  c = c + 1;
  x = x*z + 1;
  y = y*z;
}
/*@ assert 1+x*z-x-z*y == 0; */
\end{lstlisting}
When the assertion is visible, the clause
\texttt{loop invariant 1+x*z-x-z*y == 0;} can be copied directly.
When it is hidden, the same nonlinear relation must be recovered from the
coupled updates to \texttt{x} and \texttt{y}.  This example illustrates the
difference between proving a supplied candidate and discovering the loop
relation needed by a held-out target.
